# SPEC-06：角色模拟连续主旅程

## Problem Statement

现有自动执行器仅覆盖运行配置、身份与上报，无法证明事件受理、审批、经验复用和重启恢复连成同一个真实故事。验收仍依赖人工拼接记录。

## Solution

让自动化执行者使用独立角色账号完成 E2E-00～16，在一个新验收 run 中保留连续业务关系，最终由第二名员工复用刚发布的经验，并验证 App 重启后的恢复。

## User Stories

1. 作为验收负责人，我希望自动完成整条主旅程，以便减少重复人工点击。
2. 作为员工，我希望以自己的正式身份上报并上传附件，以便受理结果可追溯。
3. 作为员工，我希望补充信息进入原事件，以免生成重复工单。
4. 作为经理，我希望看到有依据建议及真实来源，以便决定采纳、忽略或不等待。
5. 作为经理，我希望采纳决定明确留痕，以便证明任务不是未经授权自动派发。
6. 作为员工，我希望任务按依赖解锁，以便按正确顺序完成处置。
7. 作为经理，我希望拒绝后能收到补证和重提，以便审批流程真正闭环。
8. 作为员工，我希望批准后的通知、接单与回执关联，以便证明工作已交接。
9. 作为经理，我希望关闭前校验条件并运行巡检，以免未解决风险被关闭。
10. 作为专家，我希望访谈可恢复且原意需我确认，以免生成错误经验。
11. 作为知识负责人，我希望退回、修订、审核和发布保留版本，以便治理知识质量。
12. 作为第二名员工，我希望在独立会话命中新经验并记录采用，以便证明经验可复用。
13. 作为管理员，我希望一个业务编号能查看完整事件与八 Agent 证据，以便核验链路。
14. 作为员工，我希望重启后能继续处理中会话，以便不中断业务。
15. 作为审计员，我希望自动操作明确标识为内部角色模拟，以免被误当真人签收或专家真实授权。
16. 作为验收执行者，我希望失败时保留结果并停止依赖步骤，以便定位真实阻断点。

## Implementation Decisions

- 扩展现有 UAT CLI 与正式 HTTP 客户端，保留 E2E-00～02，增加后续步骤；沿用已有证据目录和固定旅程 ID。
- 开始前只准备隔离场地的主数据、账号、授权和已发布 SOP，记录无本次业务过程数据的基线；不得预填事件、完成任务或经验复用结果。
- 各角色使用独立认证和会话。普通员工路径真实使用员工凭据，内部渠道可使用其正式受控身份映射；不能用管理员替所有角色执行权限测试。
- E2E-03～04 核对四 Agent 同一消息链、来源引用与事件唯一；E2E-05～06 核对四任务、三依赖、负责人和结构化回执。
- E2E-07～09 必须真实执行首次拒绝、补证重提、批准及内部唯一送达；E2E-10～12 验证关闭门禁、真实 Watcher、关闭和可重试经验候选。
- E2E-13～14 覆盖可恢复访谈、专家确认、退回、修订、复审和发布；保持专家/知识负责人权限分工与不可变版本。
- E2E-15 以第二员工独立会话提出新问题，引用本次发布的经验及 SOP，保存版本和采用记录；核对八 Agent 在同一故事下的真实调用。
- E2E-16 在受控处理中状态只重启 App，记录实例变化、其他服务未重启、消息领取与 ACK；单纯空闲重启不算恢复验收。
- 正式接口推进状态，数据库只读核验；UI 核对可读业务卡、等待、错误和刷新恢复。
- 业务角色模拟不改变生产权限，也不自动签署真实客户或专家法律授权；验收账号与数据标识为内部测试。
- 不支持或未执行的步骤返回明确错误；异步等待有截止时间和诊断，不能无限轮询。失败包保留，修复后新建 run。

## Testing Decisions

- 最高边界为 UAT CLI 驱动正式 API/UI，观察业务卡、查询结果、队列、审计与调用事实。
- 复用现有 UAT journey、baseline、事件卷宗、任务、审批、经验生命周期和运行恢复测试。
- 固定客户端响应只用于执行器分支测试；最终通过必须来自真实 PostgreSQL、Redis、pgvector、模型及 App 重启。
- 对各阶段关联 ID、角色、引用版本和去重逐项断言；缺任一阶段不允许通过拼接旧记录补齐。
- 对员工、经理、专家、知识负责人、管理员各取独立会话验证，明确管理员代理映射路径和普通员工路径的差别。

## Out of Scope

假业务数据演示、直接数据库推进、真实外部通知、客户签收、13 条故障旅程的全部实现及新增业务功能。

## Further Notes

映射 R4；依赖 SPEC-01～05 的合同与运行基础。补充治理和四入口全量等价由 SPEC-08 覆盖，主旅程成功不能独自提升全部功能。

## ADDED Requirements

### Requirement: 主旅程使用独立角色与连续业务来源
执行器 SHALL 在同一新 run 中按正式权限完成 E2E-00～16，MUST NOT 用管理员会话替代所有员工操作或直接改库完成流程。

#### Scenario: 上报后补充
- **WHEN** 员工完成带附件上报并在同会话补充信息
- **THEN** 系统保持一个事件和可追溯消息链，后续任务、审批及经验关联该来源

### Requirement: 任务与审批体现人工角色决定
执行器 SHALL 验证建议决定、任务依赖、审批拒绝与重提，并在批准后核对唯一内部送达。

#### Scenario: 首次审批被拒
- **WHEN** 经理拒绝第一次审批，员工补证后重新提交
- **THEN** 拒绝阶段无动作执行，第二次审批关联前次记录，批准后每个接收对象的业务送达不重复

### Requirement: 第二员工复用本次发布版本
执行器 SHALL 由第二名员工以独立身份检索和采用本次治理发布的经验。

#### Scenario: 新员工咨询已发布经验
- **WHEN** 专家确认、退回修订与复审发布完成后，第二员工提出新问题
- **THEN** 响应引用本次经验的有效发布版本及 SOP，并存在同一业务来源链的采用记录

### Requirement: 重启恢复必须发生在处理中状态
执行器 SHALL 保留 App 实例、队列和业务唯一性证据，MUST NOT 将无在途工作的重启当作恢复验收。

#### Scenario: App 处理中重启
- **WHEN** 已核验存在待恢复工作时只重启 App
- **THEN** App 实例改变，数据服务未重启，原工作被恢复并 ACK，会话可继续且业务结果唯一

### Requirement: 未执行步骤不得产生成功
执行器 SHALL 在不支持、环境阻断或步骤失败时如实保留状态并停止依赖步骤。

#### Scenario: 经验发布失败
- **WHEN** 发布未形成有效索引版本
- **THEN** 后续经验复用不能记录通过，失败证据保留且不借用旧经验替代
