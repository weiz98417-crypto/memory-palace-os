# SPEC-09：证据驱动的注册表就绪发布

## Problem Statement

直接修改注册表状态不能证明能力可用；旧记录、空路径或只通过主旅程可能使静态 READY 与真实环境矛盾。禁用外部渠道也不应该被强制伪装成可用。

## Solution

从已验证的完整运行和当前环境事实生成可审查的注册表候选，逐项检查证据再应用，并输出内部验收报告和仍未满足的交付门禁。

## User Stories

1. 作为发布负责人，我希望先看到候选差异，以便知道哪些能力真正得到证据支持。
2. 作为管理员，我希望注册表与当前运行事实一致，以免页面显示虚假可用。
3. 作为审计员，我希望 READY 可回溯当前 run，以便复查来源和版本。
4. 作为验收负责人，我希望缺少补充治理或浏览器证据时保持阻断，以免一条主线替代全量验收。
5. 作为经理，我希望 DeepSeek 只有真实调用通过后可用，以免依赖假模型建议。
6. 作为交付人员，我希望禁用渠道仍显示正确原因，以免用户误以为能收发消息。
7. 作为发布负责人，我希望禁用行为验证可满足相关旅程，以免被错误要求启用生产渠道。
8. 作为运维人员，我希望依赖故障能反映到当前可用状态，以免历史通过遮盖实时故障。
9. 作为验收负责人，我希望失败候选不破坏原注册表，以便安全重复执行。
10. 作为产品负责人，我希望内部验收与客户、视觉、容量和持续运行结论分开，以便准确判断交付范围。
11. 作为开发者，我希望规格 ready-for-agent 与功能 READY 明确区分，以免任务标签冒充业务完成。

## Implementation Decisions

- 复用功能注册表、FEATURE_REQUIREMENTS、运行时聚合与发布门禁，不新建第二套就绪真相。
- 输入为 SPEC-01 完整封包、SPEC-06/07 的 30 条旅程、SPEC-08 覆盖矩阵及本次环境事实；记录来源 run 与实际版本指纹。
- 先离线生成候选、校验结构及所有引用，再与当前运行快照逐项对照；正式写入采用原子替换或等效完整写入，并能恢复前一版本。
- 候选生成不要求正式注册表提前 READY；全量证据封包也不依赖候选被应用，避免循环验收。
- 20 个业务、8 个 Agent、5 个平台与 DeepSeek 共 34 项仅在各自要求全部满足后提升；不能以硬编码“34”替代逐项验证。
- 企业微信保持 DISABLED_BY_POLICY；无供应商配置和验收的短信/语音保持 DISABLED_REQUIRES_CONFIG。safe_disabled_verified 由真实拒绝与零副作用证据证明，不能人工补 true。
- 30 条旅程各自要求步骤通过及覆盖项满足；允许已验证禁用作为既有可选外部集成例外。禁用旅程 READY 不代表渠道 READY。
- 不把旧截图、旧模型/向量架构、缺失文件、测试夹具或其他 run 的记录作为当前通过证据。
- 运行时依赖退化必须重新反映为当前阻断/降级，保留历史成功而不以它压过当前事实。
- 输出明确区分内部自动验收、当前运行就绪、四入口视觉/切流、目标环境持续运行、容量和客户签收。客户/视觉未签不能被生成器自动代签。

## Testing Decisions

- 最高边界为候选生成/应用命令与注册表查询，复用注册表单元测试、诊断集成测试和证据验证测试。
- 覆盖结构正确但记录空、跨 run、篡改、当前环境不健康、模型 Mock、缺 Agent、只有主路径等反例。
- 验证 34 个合法内部/模型能力与 3 个已验证禁用项可以满足既有内部发布门禁；缺禁用证据则不能通过。
- 验证中途写入失败不产生半份注册表，重复生成相同证据的候选内容稳定。
- 最终核对真实 API 返回的状态、明细和阻断原因，不只搜索 YAML 中 READY 字符串。

## Out of Scope

启用生产外部渠道、绕过真实验收、改变客户合同、自动签收视觉、生产部署发布及替代长期运行测试。

## Further Notes

映射 R6；依赖 SPEC-01～08。ready-for-agent 是规格交接标签，不是运行状态。目标 34 READY + 3 已验证禁用 + 30 旅程 READY 仅描述通过条件，当前状态不变。

## ADDED Requirements

### Requirement: READY 必须来自当前可核验证据
注册表系统 SHALL 逐项验证当前运行、版本、覆盖矩阵和真实环境后生成候选，MUST NOT 通过直接改状态完成验收。

#### Scenario: 只有主旅程成功
- **WHEN** 主旅程通过但故障步骤或某功能补充证据缺失
- **THEN** 候选保留相关阻断原因，正式注册表不被全量提升

### Requirement: 安全禁用可满足例外但不改变渠道状态
注册表系统 SHALL 保留外部渠道禁用状态，并仅在安全禁用有证据时允许其满足相关旅程。

#### Scenario: 未配置短信但禁用已验证
- **WHEN** 短信没有供应商配置，受限操作被拒绝且无发送副作用
- **THEN** 短信仍为 DISABLED_REQUIRES_CONFIG，相关禁用旅程可通过，不声称短信发送成功

### Requirement: 候选验证与应用具有完整性
注册表系统 SHALL 在全部检查成功后完整应用候选，失败时保留可用的原版本。

#### Scenario: 应用期间写入失败
- **WHEN** 候选已生成但正式写入发生错误
- **THEN** 不留下部分更新的注册表，错误可诊断且原状态可恢复

### Requirement: 当前运行退化不能被历史 READY 遮盖
注册表系统 SHALL 根据当前依赖和运行事实报告可用性，同时保留历史验收记录。

#### Scenario: 验收后模型服务失效
- **WHEN** 历史模型验收成功但当前模型配置或服务不可用
- **THEN** 当前状态反映故障与原因，历史验收仍可追溯但不覆盖实时诊断

### Requirement: 内部验收与其他交付门禁分开呈现
发布报告 SHALL 明确显示内部自动验收和独立人工/持续运行门禁，MUST NOT 自动宣告未执行事项通过。

#### Scenario: 内部验收完成但客户未签收
- **WHEN** 所有内部要求满足而客户、持续运行或视觉签收仍待完成
- **THEN** 报告内部结果及待办门禁，不将其合成为无条件客户交付完成
